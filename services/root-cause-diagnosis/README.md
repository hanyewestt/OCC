# Root Cause Diagnosis (WQAP-3)

Root Cause Diagnosis is the event-neutral diagnosis service. Its first implemented
vertical slice diagnoses confirmed `BUS_BUNCHING` events in `SIMULATION` only. It
does not detect events, change producer facts, generate mitigation recommendations,
or execute operational directives. The API recognizes a small set of event types,
but non-bunching types return `422` until their fact sources, evidence adapters,
cause taxonomies, and downstream contracts exist.

## Stack

Java 25, Spring Boot 4.1.1, Maven, Spring AI 2.0.1 with the Google GenAI starter,
`gemini-3.1-flash-lite`, PostgreSQL 18.6, Spring Data JPA, Flyway, Docker/Compose,
Testcontainers, OpenAPI 3.1 via springdoc 3.1.1, and Swagger UI. All service URLs,
ports, credentials, timeouts, retry settings, evidence windows, score thresholds,
and Gemini parameters are externally configured. See the repository-root
`.env.example` for the complete safe configuration inventory.

## Flow and ownership

```text
WQAP-2 confirms two consecutive simulation samples
  -> transactionally stores canonical alert + diagnosis outbox item
  -> retries POST /internal/v1/diagnosis-requests with a stable Idempotency-Key
  -> WQAP-3 fetches canonical WQAP-2 facts and simulation evidence from ingestion
  -> one bounded Spring AI structured diagnosis (+ at most one schema repair)
  -> Java validates evidence citations and calculates evidence-support score
  -> diagnosis + exact recommendation payload are persisted before delivery
  -> retries POST /internal/v1/bunching-recommendations with the persisted key/body
  -> WQAP-4 owns recommendation generation
```

WQAP-2 facts are read from `GET /internal/v1/bunching-alert-events/{eventId}` and
are not regenerated by this service. Context is read through ingestion's
`GET /internal/v1/demo-runs/{demoRunId}/root-cause-context`. The RCA service never
queries another service's database. Durable queues use PostgreSQL row locks and
leases; external HTTP/AI calls happen outside queue-claim transactions.

Only `SIMULATION` events are submitted for recommendation. WQAP-2 does not enqueue
`OBSERVATION_ONLY` detections. If one nevertheless reaches this service, it is
terminally rejected and cannot start operational planning. Completed diagnoses are
submitted even when their confidence is below the configured review threshold.
Low confidence is preserved and explained as a limitation; the score is never
raised to force downstream submission.

## AI and confidence policy

Spring AI uses one structured `ChatClient` call with a constrained cause schema; the
application permits at most one validation-repair call. No model tools, database
access, MCP, memory, vector store, or model-directed service retrieval are enabled.
The internal evidence snapshot is typed and treated as untrusted data. Provider
structured output controls shape only; Java independently validates cause codes,
subtypes, and every cited evidence ID.

The deterministic `bunching-evidence-support-v1` score combines provenance,
temporal alignment, spatial alignment, incident specificity, and headway chronology.
It is an explainable support score, not a calibrated probability of causation. The
score is capped at `0.85` to reflect the limited causal strength of correlated MVP
evidence. `UNKNOWN` has confidence zero and retains the detector's canonical evidence
IDs. The default `0.70` threshold is descriptive only, not a trigger gate.

The event uniqueness key is `(eventType, producer, eventId, schemaVersion)`.
Recommendation delivery persists the UUID idempotency key and byte-stable payload
before the first request; all retries reuse both. Transient failures are retried with
bounded exponential backoff and jitter. Transient producer-to-RCA and RCA-to-WQAP-4
delivery retries are unlimited by default (`*_MAX_ATTEMPTS=0`) with a capped one-minute
delay; set a positive limit only when a deployment has a dead-letter replay process.
Client validation/conflict errors remain terminal.

## Run locally

Create the ignored root `.env` from `.env.example`, then replace the placeholder
database, Gemini, and DataMall credentials. The diagnosis process validates the Gemini
key at startup; a real `OCC_DIAGNOSIS_GEMINI_API_KEY` is required to run the AI path.
From the repository root, start PostgreSQL and the services with:

```powershell
docker compose --env-file .env -f infra/local/compose.yaml up -d --build
```

The local Compose ports are ingestion `6767`, bunching detection `6768`, recommendation
engine `6769`, root-cause diagnosis `6770`, and PostgreSQL `5432`. Containers call one
another using Compose service DNS and internal ports (`8001`–`8004`). The database
init script provisions the dedicated `occ_diagnosis` role/schema; Flyway creates the
diagnosis tables at service startup.

For an IDE/Maven run, use the `local` profile from this service directory so
`application-local.yml` imports the repository `.env`. Host-native calls use the
`*_PUBLIC_URL` settings; Compose uses the separate `*_INTERNAL_URL` settings.

## API and operations

- `POST /internal/v1/diagnosis-requests`: queue a producer-owned event reference;
  requires a UUID `Idempotency-Key` header.
- `GET /internal/v1/diagnosis-requests/{requestId}`: read request status and the
  diagnosis ID when available.
- `GET /internal/v1/diagnoses/{diagnosisId}`: read the completed diagnosis,
  and downstream recommendation-delivery status/failure code.
- `GET /actuator/health`: liveness/readiness health.
- `GET /v3/api-docs` and `/swagger-ui.html`: generated OpenAPI 3.1 contract and UI.

Use RFC 9457 `application/problem+json` for rejected requests. API bodies use synthetic
examples only. The ungrouped docs/API endpoints are not an authorization mechanism;
deployments must provide network-level protection for the internal service endpoints.

To export the runtime-generated OpenAPI contract, start the service and run
`./mvnw -Popenapi org.springdoc:springdoc-openapi-maven-plugin:1.5:generate`
(PowerShell: `./mvnw.cmd -Popenapi org.springdoc:springdoc-openapi-maven-plugin:1.5:generate`).
This writes `openapi/root-cause-diagnosis.json`; override
`-Dopenapi.apiDocsUrl=http://localhost:<port>/v3/api-docs` for a non-default port.

Operational history stores immutable evidence snapshots for completed diagnoses,
snapshot hashes for provider attempts, validated outputs, sanitized model/provider
metadata, and recommendation-delivery status. It deliberately does not store API
keys, rendered prompts, raw provider responses/errors, or stack traces.
