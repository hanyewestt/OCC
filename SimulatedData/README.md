# Simulated fleet data — service 190

Deterministic test and demo data for bus-bunching detection and mitigation.
Generated by [generate_route190.py](generate_route190.py) (Python 3, stdlib only):
Run these commands from the repository root.

```powershell
py SimulatedData/generate_route190.py            # default seed 190
py SimulatedData/generate_route190.py --seed 7   # different but still valid run
```

```bash
python3 SimulatedData/generate_route190.py            # default seed 190
python3 SimulatedData/generate_route190.py --seed 7   # different but still valid run
```

The script refuses to write output if the bunching scenario fails to trigger
the rule, or if the normal scenario triggers it.

## Why this exists

The live DataMall Bus Arrival feed has no vehicle identity: it can show that
"the 1st and 2nd 190 at stop 44251 are 3 minutes apart", but not *which* bus
to instruct. `project-v2.md` §6 therefore limits live data to dashboard
warnings; directives are only issued to simulated buses that are unambiguously
identified. This folder is a self-contained synthetic fixture. Its plates and
drivers are invented test data, never identities assigned to DataMall arrivals.
The planned hybrid map can pin real observations as context and inject a demo bus
with a stable assignment; it does not turn a live arrival slot into an identified
vehicle. See [the hybrid fleet demo design](../docs/architecture/hybrid-fleet-demo.md).

## Files and how they line up with the rest of the repo

| File | One row = | Matches |
|---|---|---|
| `fleet_telemetry.jsonl` | one bus, one minute (07:30–08:30) | Same field names as `bus_telemetry_normal.jsonl` on the `my-changes` branch, plus `direction`, `trip_id`, `stop_sequence`, `at_stop`, `passenger_count` and `speed_kmh`. Covers the columns of `bus_telemetry` in `database/init/01-schema.sql` (`vehicle_plate` ← `bus_plate`, `passenger_load` ← `load_status`, `timestamp` ← `recorded_at`). |
| `bus_arrivals_v3.jsonl` | one monitored stop, one poll | Shaped like `ingestion.raw_observation` (`source`, `source_key`, `request_parameters`, `http_status`, `fetched_at`, `payload`), with `payload` in the DataMall **Bus Arrival v3** format that `BusArrivalPoller` stores. The same parsing and detection code can therefore run on live and simulated data. |
| `traffic_incidents.json` | — | DataMall TrafficIncidents shape (`Type`, `Latitude`, `Longitude`, `Message`). This is the evidence for the AI's root-cause step. |
| `scenario.json` | — | Route-profile values, fleet roster (plate ↔ Bus Captain ↔ trip), events, the **expected detection**, **reference directives**, holds applied, metrics and per-stop headways for bus A and bus B. |

`bus_arrivals_v3.jsonl` rows carry a `_truth.next_bus_plates` field saying which
simulated bus each `NextBus` really was. It is for scoring tests only; strip it
before feeding anything that should behave like the live system.

## What the bunching scenario shows (seed 190)

| | Normal | Bunching | Bunching + holds |
|---|---|---|---|
| Passenger waiting (pax-min) | 8,436 | 8,983 | 8,707 |
| B's gap to A at the terminal | 524 s | 45 s | 408 s |

1. **07:34** A vehicle breakdown on Teck Whye Ave delays bus A (`SBS8027Y`, the 07:30 trip) by 5 minutes.
2. A is now about 15 min behind the bus ahead, so it finds more passengers waiting, dwells longer and loses more time. B (`SBS5898U`, the 07:40 trip) finds fewer passengers and catches up.
3. **07:45** At stop 44251 (Bt Panjang Stn), NextBus and NextBus2 are 276 s and then 221 s apart on two consecutive polls. Both are under 0.5 × 600 s, so bunching is **confirmed**.
4. Reference directives: **A proceeds with no hold. B holds 120 s at control stop 44241**, and again at later control stops (120, 120, 87 s). No bus is told to speed up.
5. Without action, B stays under 100 s behind A from Stevens onwards, often 30–45 s. With the holds, the gap recovers to about 400 s.

## Rules encoded (from `project-v2.md`)

- Bunching: headway ≤ 0.5 × planned headway on 2 consecutive one-minute polls,
  same service and direction. NextBus3 ≥ 1.5 × headway raises severity.
- Entries with `Monitored = 0` (timetable estimates, not live GPS) are ignored.
- Hold only the follower, only at a control stop, at most 120 s per hold, only
  after controller approval (modelled as 90 s after confirmation).

## Assumptions to confirm with the team

These are fixture values, not facts from the repo:

- Planned headway 600 s. Check against DataMall `BusServices.AM_Peak_Freq` for 190.
- Operator code `SBST`. Check against DataMall `BusServices`.
- Control stops `44241`, `40239`, `09037`, `04229` and monitored stops
  `44251`, `40229`, `09047`, `08057`, `04149` are demo choices.
- Demand rates, speeds, dwell coefficients and vehicle capacities are round
  plausible numbers, not calibrated to real ridership.
- Bus plates are fictional (they have a valid check letter). Bus Captain IDs are fictional.
- Stop topology is from LTA DataMall via `data.busrouter.sg` (Singapore Open
  Data Licence), snapshot 2026-09-23.
- Only direction 1 (towards the city) is simulated.
