## Traffic incident lifecycle

Use a provider-neutral synthetic incident key, fixed timestamps and complete poll identifiers. Assert one OPENED event for the first complete observation; a replay creates nothing; a changed type/message/coordinates produces one UPDATE; two repeated identical observations produce no duplicate update; two subsequent successful complete polls scoped to the same feed and explicitly omitting the key produce one CLEARED transition only after the configured absence/freshness rule is met. An HTTP failure, timeout, partial response, stale feed, wrong demo run, or replay cannot increment the absence count or clear the active incident. A later observation after clear reopens the same scoped incident identity or a new episode according to the explicitly documented episode rule.

Traffic and bunching fixtures run together in the same Disruption application. Each produces its own typed Planning event; traffic evidence is never represented as an arrival-observation FK and never enters bunching-only headway or mitigation rules. Historical Ingestion incident observations are retained as facts and are not emitted as synthetic Planning events during schema import.
