Our project will use microservices architecture. Each functionality will be its own service, and services 
will be containerized/dockerized, managed through Docker Compose, and will be deployed on EC2 on 
AWS. For frontend, we will have a nginx container serving static React frontend pages. Web traffic to our 
app will be routed through nginx. API requests (along with authorization header and tokens from external 
auth provider, Supabase Auth) will be forwarded by nginx to the API Gateway (Spring Cloud Gateway) 
and  forwarded  to  respective  services.  Our  internal  backend  services  (planning,  ingestion, 
bunching/disruptions)  will  share  the  same PostgreSQL database, but will have isolated schemas and 
different DB roles. 
 
Database Design 
 
Diagram: https://drive.google.com/file/d/1J7ojenMzCQlLOwIbL4sB9N7GrfrMLPOf/view?usp=sharing  
There will be 3 main schemas in our app: Ingestion, Disruptions, and Planning. 
Ingestion will contain data from the LTA Datamall API. Disruptions will contain relevant disruptions events 
like incidents and bus bunching. Planning will contain analysis and recommendation data. 
 
 
API Design 
As explained in the software architecture, we will have an API Gateway to route public requests to the 
internal  services.  They  will  be  accessible  from  /api/v1/<service-name>  (planning,  ingestion, 
bunching/disruption). Services will also be able to communicate with other services through the internal 
API through /internal/v1/ paths, these will not be accessible publicly. We also have Swagger UI for both 
internal and public APIs as presented in the midterm demo. 
 
Security Design 
Current security design: 
-  Each service uses a dedicated PostgreSQL account and schema, limiting database access 
across services. 
-  Credentials and API keys are supplied through environment variables (.env) 
-  API requests have validation checks like required fields, acceptable values, string lengths, etc. 
-  Gemini uses structured evidence and outputs that are checked by deterministic rules, ensuring 
recommendations target approved buses and stops, respect safety limits, and fall back to 
deterministic results when invalid. Actionable recommendations are currently restricted to 
validated simulation scenarios, while payload limits, timeouts, retry limits, and secret redaction 
help control resource use and protect credentials. 
Future additions to security design: 
-  Implement Supabase Auth to manage user sign-in and issue access tokens for authorization and 
authentication purposes 
-  Application roles such as ADMIN, CONTROLLER, and DRIVER will be assigned through trusted 
administrative processes. 
-  Add  a  nginx  proxy  to  manage  web  traffic,  and  add  an  API  gateway  to  manage  requests  to 
backend services, and do authorization checks before routing and forwarding the requests. 

Continuous Integration and Testing Details 
Initially tests were done through manual Swagger UI checks and API calls of our API endpoints through 
Postman. However this became troublesome as the app grew. The current approach uses these tools: 
Tool | What is tests 
JUnit | Runs automated tests and checks expected results—for example, whether the 
bunching policy correctly detects buses arriving too close together 
Spring Boot Test | Starts  the required Spring components to test application wiring and service 
behaviour 
Mockito | Replaces dependencies with controlled fake behaviour, so tests can simulate 
provider failures without calling real external APIs 
MockMvcTester | Sends  simulated  HTTP  requests  to  controllers  and  checks  status  codes, 
validation errors, and JSON responses without starting a separate web server 
Testcontainers | Starts  temporary  PostgreSQL  containers  to  test  actual  database  queries, 
constraints, transactions, and migrations 
Maven Surefire / Failsafe | Run the tests: Surefire handles *Test classes; Failsafe handles *IT integration 
tests during mvn verify 
Swagger UI + Postman | Supports  manual  endpoint  testing  by  letting  developers  send  requests  and 
inspect responses 
In  future  sprints,  we  plan  on  adding  in  full-system  tests covering ingestion -> disruption detection -> 
planning, authentication and permissions, browser tests for the controller and captain views, AI output 
evaluation, and load tests to check restarts, provider failures, latency, and resource usage. 
 
For continuous integration (CI), we have yet to implement full automated CI in our apps. However, we 
have  implemented  and  ran  some  testing  manually  as  explained  above  on  our  DB  migrations  and 
integrations, Docker builds, and automated tests. 
 
In future sprints, we plan on adding in Github Actions for CI. This automated CI workflow will: 
-  Build all backend services and their Docker images, run automated tests, and scan the images 
for vulnerabilities using Trivy. 
-  Validates API specifications and detects breaking contract changes using oasdiff. 
-  Run DB integration checks 
-  Frontend checks
