## 1. Agent mission and stop condition

**Core phase 1 — Refactor first:** create Disruption by consolidating bunching and traffic incident detection, create Planning by consolidating diagnosis and recommendation, and preserve Ingestion, existing workflow behavior, deterministic recommendation safety, demo isolation, retry recovery and retained AI evidence. Deliver reproducible local/CI setup, safe schema migration, canonical APIs, gateway/authentication/authorization, testing design and execution, and an MVP EC2 deployment/runbook package.

**Core phase 2 — New/additional features later:** separately add authoritative vehicle/captain identity data integration and authenticated captain binding, approval/rejection, assigned instructions and the corresponding controller/captain React journeys. Identity source availability and safety validation govern any future live use; these capabilities are not prerequisites for completing core phase 1.

The target comprises four Java applications: **Ingestion, Disruption, Planning, Gateway**. Gateway owns no business tables. For the MVP deployment, Nginx is the proposed public TLS edge; the local Compose stack serves the temporary auth test page from Gateway and does not start a separate Nginx container. Three backend services own `ingestion`, `disruption`, and `planning` schemas in one PostgreSQL/PostGIS instance. Supabase owns authentication, not the OCC operational database.

Finish the requested core phase when its own work-package gates and acceptance matrix pass with saved evidence, including removal of unused files. **The default implementation handoff executes core phase 1 only and stops before core phase 2.** Do not add phase-2 tables, endpoints, configuration, UI or empty feature scaffolding during phase 1. Preserve existing demo captain/vehicle metadata needed by existing recommendation rules; it does not establish authenticated captain binding. Do not call skipped Docker tests, mocked providers, generated but unexecuted commands, or an unperformed production deployment verified. Report those boundaries explicitly. Do not provision paid resources or destroy legacy schemas as a side effect of a code refactor; prepare those steps for the authorized deployment operator.

### Clean startup and migration ownership

Reuse the existing Compose service definitions/health checks, but move the canonical base to root `compose.yaml` and remove duplicate init paths after verification. Root `compose.override.yaml` contains local build/debug-port differences only. Production uses explicit `-f compose.yaml -f infra/compose.production.yaml`; test runs use an explicit test override. Do not repeat the full stack in each file. Compose automatically loads its conventional local override only when those files are not explicitly selected. [Compose override guidance](https://docs.docker.com/compose/how-tos/multiple-compose-files/merge/)

Startup graph: **healthy Postgres -> successful db-bootstrap -> successful per-schema Flyway job -> owning application**. Gateway/Nginx wait for their required upstream health. Use `service_healthy` and `service_completed_successfully`; no custom shell readiness loops. [Compose startup conditions](https://docs.docker.com/compose/how-tos/startup-order/)

- **Postgres container:** database storage and health only. Map its own admin initialization environment; do not give it every service credential or mount a shell init directory.
- **One `db-bootstrap` job:** invoke `psql --set ON_ERROR_STOP=1 --file /bootstrap/bootstrap.sql` directly using a pinned PostgreSQL-compatible image. The one SQL file creates/verifies PostGIS, service roles, schemas, grants/default grants. It is safe on fresh/existing volumes and does not drop data, seize unexpected ownership or rotate passwords silently. Read canonical environment into psql variables using `\getenv` and quote values as SQL data; do not interpolate passwords into shell commands or commit them in SQL. Admin credentials belong only to this job. [psql variable commands](https://www.postgresql.org/docs/18/app-psql.html)
- **Three Flyway jobs:** `ingestion-migrate`, `disruption-migrate`, `planning-migrate`, using a pinned compatible official Flyway CLI image and service-owned migration directories. Share repetitive job configuration via a small Compose anchor; each job gets only its own migrator credentials/history/schema. Flyway creates/updates business tables, while service runtime keeps Flyway disabled and Hibernate `validate`. Use packaged immutable migration assets for deployment; local jobs may mount source SQL read-only. [Flyway CLI](https://documentation.red-gate.com/flyway/reference/usage/command-line)
- **Runtime containers:** only their own low-privilege credentials. No app process bootstraps roles, executes provisioning shell scripts or runs privileged DDL. Gateway has no migration job.

Postgres image entrypoint init files run only for an empty data directory, which makes them insufficient for existing-volume upgrades. The explicit bootstrap/migration jobs avoid that ambiguity. Keep job execution visible in Compose logs; failures block the owning service. On each release explicitly recreate/run bootstrap and migration jobs before starting the new runtime images; do not assume a previous exited-successful job has applied a new release. Validate fresh startup, restart and existing-volume upgrade without deleting volumes. [Postgres image initialization behavior](https://hub.docker.com/_/postgres)

Keep one genuine one-time legacy data import SQL/tool when needed; remove the old per-schema `*.sh` provisioning scripts and duplicated schema-init service definitions after this path passes. This simplification retains database permissions and recovery proof without a new general-purpose setup framework.

## 7. Minimal setup/build/test entry points

These are target commands to implement and verify, not commands already supported by the current tree. Compose owns local infrastructure/startup and Maven owns Java builds/tests. Keep one root wrapper and direct cross-platform tool commands; no `verify.ps1`/`verify.sh` pair per concern, no shell service-discovery loop, no duplicate task runner.

```powershell
# One-time developer configuration; fill in the ignored file locally.
Copy-Item .env.example .env

# Local startup: Compose automatically reads compose.override.yaml.
docker compose config --quiet
docker compose up --build -d --wait

# Whole Java build + unit/API/architecture/DB tests.
.\mvnw.cmd --batch-mode --no-transfer-progress verify

# One service with required reactor dependencies.
.\mvnw.cmd -pl services/planning -am verify

# Target Maven profiles for contract and full-system verification.
.\mvnw.cmd -Pcontracts verify
.\mvnw.cmd -Psystem-tests verify

# Operations use Compose directly.
docker compose ps
docker compose logs -f planning disruption
docker compose stop

# Production explicitly excludes the automatically loaded local override.
docker compose -f compose.yaml -f infra/compose.production.yaml config --quiet
```

On Linux use `./mvnw` for the same goals. Root `.env` is Compose's local deployment interface; Java-native runs retain the documented local import or explicitly supplied environment. Do not assume Maven automatically reads `.env`.

Fresh/legacy migration checks are named PostgreSQL/Testcontainers integration tests run by `verify`, not two additional scripts. Contract export/check is a Maven profile with explicit application startup/readiness/export/stop and semantic compatibility checks. Full-system fixtures/lifecycle can be managed by an exercised integration-test module/profile invoking Compose in an isolated project, with controlled cleanup and sanitized reports. CI calls these same commands directly.

For deterministic system checks, use `compose.yaml` plus `infra/compose.test.yaml` with generated test-only environment and a unique project/volume identity; never consume the developer's or production `.env`. Test helpers must have deadlines and verified cleanup scope. Keep any nontrivial helper inside the owning test module; add a standalone script only if direct Maven/Compose/npm commands cannot handle a demonstrated need.

Phase 2 frontend uses `npm ci` and `npm run lint`, `typecheck`, `test:unit`, `build`, and `test:e2e` from the owning frontend/test package. Playwright and k6 run through pinned CLI/container commands, with fixture URLs/settings supplied at runtime. Do not create extra wrapper scripts solely to rename those commands.

No setup/build implementation may depend on `infra/local/postgres/init` scripts, obsolete per-schema shell jobs or repeated per-service Maven wrappers in the final tree. A genuinely necessary migration/import SQL file and tested backup/restore procedures remain purposeful artifacts, not an excuse for a new script hierarchy.
